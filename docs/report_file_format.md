# レポートファイル フォーマット仕様

[ood_news_agent/cli.py](../ood_news_agent/cli.py) は、実行するたびに調査レポートを
標準出力に表示するのと同時に、`$OUTDIR/report_YYYYMMDD_HHMM.md` としても
保存します。書き込み処理は `write_report_file` 関数が担います。

保存されるのは、調査担当Agentの構造化出力(`OODReport`)を執筆担当Agentが
再構成したニュースレター記事(`OODArticle.article_markdown`)です。調査担当Agentが
出力する構造化項目(`OODReport.entries`)から`templates/report_markdown.j2`で
生成する箇条書き中心の報告文は、執筆担当Agentへの入力としてのみ使われ、ファイルにも
標準出力にも現れません。

調査ログ(`ood_research_log_*.json`、[docs/ood_research_log_format.md](ood_research_log_format.md)
参照)とは別物です。レポートファイルは「その回の実行で得られた最終的な報告文」の
スナップショットであり、過去の実行分と統合・追記されることはありません。

調査結果に新規・更新項目がない場合は、執筆担当Agentを実行しないため、標準出力にも
レポートファイルにも記事は出力されません。

このファイルもリポジトリには含めません(`.gitignore` の `/output/` で除外)。
実行環境ごとにローカルで蓄積されるものです。

## 出力先・ファイル名

```
$OUTDIR/report_<YYYYMMDD>_<HHMM>.md
```

- `$OUTDIR` は環境変数 `OUTDIR` で指定する出力先ディレクトリ。未設定時は `output`。
- ディレクトリが存在しない場合は実行時に自動作成される。
- `<YYYYMMDD>_<HHMM>` はAgent実行日時(分単位)。例: `20260811_1432`。
  実行ごとに異なるファイル名になるため、過去のレポートファイルは上書きされず
  蓄積される。
- `--base-date` で調査対象期間の基準日を過去日付にした場合も、ファイル名は
  基準日ではなく実行日時である(「いつ実行した分か」の記録として一貫させ、同じ
  基準日で複数回実行してもファイルが衝突しないようにするため)。記事本文に書かれる
  調査対象期間は基準日に従う。

## ファイルの内容

ファイルの内容は、標準出力に表示される記事本文(`OODArticle.article_markdown`)
と完全に同一のMarkdownテキストであり、ヘッダーやメタデータなどは付加されない。

本文自体の構成は、執筆担当Agentへの指示
([templates/writer_instructions.j2](../templates/writer_instructions.j2))で
以下のように規定されている。

**記事の構成と要件**

1. **記事タイトル** (`#` の見出し1つ)  
   調査対象期間を含め、今回の内容を一言で表すタイトルを置く。

2. **リード文**  
   今回の調査対象期間と、期間内の動きの要点を地の文で 2〜4 文にまとめる。

3. **カテゴリごとのセクション** (`##` の見出し)  
   新規・更新情報があるカテゴリのみセクションを置く。カテゴリは常に以下の順序で出力される
   (括弧内は `category` の識別子)：
   1. 新バージョンのリリース情報 (`new_release`)
   2. 開発ロードマップの更新・公開 (`roadmap`)
   3. セキュリティ脆弱性情報 (`security`)
   4. コミュニティイベント (`community_event`)
   5. その他のトピック (`other_topic`)

   見出しの日本語の文言は執筆担当Agentが識別子から訳して決めるため、上記は代表的な
   表記であり、実行ごとに多少ゆれる。

   ただし、更新のあったカテゴリが `other_topic` だけの場合は、セクションタイトルに
   「other」「その他」といった表現を含めない。カテゴリが1つしかない記事で「その他」と
   題しても、何に対する「その他」なのかが読み手に伝わらないためである。

4. **各セクションの本文**  
   - 箇条書きの羅列ではなく、地の文の解説記事として書く。
   - 各項目について、何が公開・更新されたのか、利用者にとって何が変わるのかを読み物として説明する。
   - 「更新」項目の場合は、前回からどう変わったのかが分かるように書く。
    - 情報源のURLは、対応する記述の直後に「出典」リンクを添える。
   - 項目どうしに関連がある場合は、その関連性にも触れて書く。

**全般的な要件**

- 日本語・敬体(です・ます調)で記述する。
- 入力された事実をすべて網羅する。
- 「[新規]」「[更新]」のような角括弧ラベルは使わず、新規か更新かは文章表現で伝える。
  (角括弧ラベルを使うのは執筆担当Agentへの入力側の形式であり、そこでは `[new]` `[updated]` と
  英語で表記する)
- 専門用語には必要に応じて短い補足を添え、Open OnDemand の運用担当者がそのまま社内で
  共有できる水準の読み物にする。
- 記事の末尾に、免責事項や「以上」などの定型句は付けない。

執筆担当AgentはWebSearchToolを使って入力の事実を補足調査できるが、検索結果から新たな
事実を記事に追加しないよう指示される。そのため、記事に現れるURL・日付・バージョン番号・
CVE ID は調査結果の転記である。

## 例

```markdown
# Open OnDemand 最新情報レポート (2026-07-14 〜 2026-08-13)

直近30日間の Open OnDemand 関連情報をまとめました。今回の期間では、新バージョンの
リリースはありませんでしたが、ロードマップ議論で新しいトピックが立ち上がり、
既報告の脆弱性 CVE-2026-26002 には情報の追記がありました。コミュニティイベントも
1件告知されています。

## 新バージョンのリリース情報

今回の期間内に新しい動きはありません。

## 開発ロードマップの更新・公開

Discourse のロードマップ／機能要望カテゴリに、ダッシュボードの MOTD (Message of
the Day) 設定オプションの見直しを提案する新規トピックが 2026-07-06 に投稿されました
([出典](https://discourse.openondemand.org/c/feature-requests-and-roadmap-discussion/48))。
運用側で告知文の出し方を調整している環境では、今後の設定項目の変更に影響する可能性が
あるため、議論の行方を追っておくとよいでしょう。

## セキュリティ脆弱性情報

既報告の CVE-2026-26002 (Open OnDemand の Files アプリに関する脆弱性) について、
2026-06-17 付で NVD の記録が更新されました。今回追加されたのは SSVC による
評価情報と、影響を受けるバージョンの情報です
([出典](https://nvd.nist.gov/vuln/detail/CVE-2026-26002))。脆弱性そのものの内容は
変わっていませんが、自環境が影響範囲に含まれるかを判断しやすくなりました。

## コミュニティイベント

公式サイトのイベント欄で、2026-08-06 開催の「Open OnDemand Tips and Tricks -
Americas」が告知されました ([出典](https://www.openondemand.org/))。運用の実践的な
知見が共有される回で、参加は無料です。

## その他のトピック

Discourse では、Slurm クラスタでの対話型アプリのジョブ投入エラーに関する相談スレッドに
返信が集まりました ([出典](https://discourse.openondemand.org/))。同様の構成を採る環境では
切り分けの手順が参考になります。
```

見出しの文言や段落の区切り、説明の詳しさなどの細部はAgentの生成結果によって
多少ゆれる(厳密なテンプレート出力ではなく、指示に沿った自然文生成であるため)。
上記は一例であり、完全に固定されたテンプレートではない。

## 調査ログとの関係

- 記事に書かれる「新規」「更新」の情報のうち、調査担当Agentが `entries` として
  構造化出力したものが、その調査回の `ood_research_log_YYYYMMDD_HHMM.json` に実行日時・
  対象期間とともに保存される。ログの `entries` に書き込むのは
  記事ではなく構造化出力であり、記事の文章表現に左右されない。
- 記事の文章表現と調査ログの項目は、内容としては対応しているが、
  書式(Markdownの構造・語順)と言語が異なる。調査結果は執筆担当Agentへ渡すまで英語で
  一貫しており、ログの `category` / `status` は `new_release` `new` のような英語の識別子、
  `summary` / `change_note` も英語である。記事の日本語(セクション見出しを含む)は
  執筆担当Agentが翻訳して生成する。Agent入力へ変換したMarkdownでは `[new]` `[updated]`
  の角括弧ラベルを使うが、記事側では使わない。
  突き合わせが必要な場合は実行日時
  (レポートファイル名の `<YYYYMMDD>_<HHMM>` と、同じタイムスタンプを持つ調査ログの
  ファイル名、およびその `datetime` と `period`)で対応付ける。
